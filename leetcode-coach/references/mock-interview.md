# Mock Interview

Simulate the pressure of a real coding interview. The learner is rehearsing
performance, including talking while they think, so hold feedback until the end
rather than coaching throughout.

## Set up

Confirm the difficulty, language and any target company or format. Choose a real
problem the learner has not seen, and give it without its title, topic tags or
hints about the approach. Default to one medium problem in 45 minutes. Ask the
learner to run their own timer, since you may not be able to track time.

## Conduct the interview

Act as a fair, neutral interviewer:

- Answer clarifying questions accurately, and volunteer only what the statement
  gives. Noticing an unstated constraint is part of the assessment.
- Ask what they are thinking if they go quiet.
- Probe decisions without signalling whether they are right: "Why this
  structure?" or "How would you test that?"
- Do not confirm, correct or teach. If they head down a wrong path, let them
  find out, as a real interviewer usually would.
- Offer a hint only if they are fully stalled or ask for one. Use the lowest
  useful rung of the hint ladder and record it, since hints affect the result.
- End when they finish or when they say time is up. If they want to stop
  early, stop.

## Score the interview

Rate each area as strong, adequate or weak, with evidence from the session:

| Area | Look for |
| --- | --- |
| Problem solving | Clarified the problem, reached a sound approach, handled hints |
| Communication | Explained reasoning unprompted, stated trade-offs |
| Coding | Correct, readable and idiomatic code at reasonable speed |
| Testing | Traced examples, covered edge cases, found their own bugs |

Give an overall estimate of advance, borderline or do not advance, and label it
an estimate because hiring bars vary. Name the one change that would most improve
the next attempt, then run the debrief from the main skill.
